Индивидуальная работа: 20 программ на 20 разных языках программирования.
Пять тем, на каждую тему — по 4 программы. Основная логика реализуется самостоятельно; для потоков, сокетов, файлового ввода-вывода и сериализации используются штатные средства языков и платформ.

## Порядок работы

Каждой задаче соответствует отдельная папка `<папка темы>/task_<номер>_<язык>/` для постановки, исходного кода и видео-презентации. Для выполнения программы используется отдельная ветка с именем `<номер темы>_task_<номер задачи>_<язык>`, например `1_task_2_ada`.

## Тема 1. Многопоточность

Папка: `1_threads/` · Задача темы: параллельный скан пространства хешей (proof-of-work на FNV-1a 64). Эталоны: Python (threading и multiprocessing), C++ (std::thread + std::atomic).

| № | Задача | Язык | Ветка |
|---|---|---|---|
| 1 | Параллельный поиск хешей на scoped-потоках с доказанной компилятором безопасностью | Rust | 1_task_1_rust |
| 2 | Параллельный поиск хешей на задачах и protected-объектах | Ada | 1_task_2_ada |
| 3 | Параллельный поиск хешей на легковесных процессах с супервизором | Erlang | 1_task_3_erlang |
| 4 | Параллельный поиск хешей на макросах потоков с замером цены типизации | Julia | 1_task_4_julia |

**1.1 Rust**. Диапазон nonce режется на непересекающиеся срезы и раздаётся потокам тремя способами: `thread::scope`, `Arc<AtomicU64>` и `mpsc`-каналы; при одинаковых входных данных результат сравнивается для разного числа потоков, что позволяет проверять корректность синхронизации. Отдельно разбираются три намеренно некорректные версии (`Rc` вместо `Arc`, два одновременных `&mut`, поток с недопустимым временем жизни ссылки): для каждой приводится ошибка компилятора, а затем сравниваются способы выявления аналогичных проблем в Python и C++.

**1.2 Ada**. Каждый кусок диапазона считает отдельная task с дискриминантом, счётчик и минимум хранит protected object, сбор результатов выполняется через рандеву и барьер входа. Вторая версия обходится вообще без protected-объекта — каждая задача отдаёт результат через собственный entry. Отдельным микробенчмарком сравнивается стоимость 10⁷ инкрементов через protected procedure, через std::atomic в C++ и через threading.Lock в Python.

**1.3 Erlang**. Процессы порождаются на каждый кусок диапазона, результаты собираются выборочным `receive` по уникальной ссылке. Измеряется, сколько сущностей способен создать язык: 1 000, 10 000 и 100 000 процессов (в пределах ресурсов системы) в сравнении с потоками ОС в C++ и Python — время создания, пиковая память и память на одну сущность. В режиме `--chaos` рабочий процесс принудительно завершается во время расчёта, супервизор восстанавливает обработку участка, итоговый результат проверяется по эталону.

**1.4 Julia**. Та же задача в трёх режимах: @threads, @spawn/fetch и @distributed. Главное измерение — влияние стабильности типов и оптимизаций: один и тот же цикл пишется без аннотаций типов, с явными `UInt64` и с `@inbounds @simd`, три времени сводятся в таблицу, а вывод `@code_warntype` используется для анализа типизации. Отдельно сравниваются первый вызов с учётом JIT-компиляции, повторные вызовы и измеренное время запуска C++.

## Тема 2. Алгоритмические задачи

Папка: `2_algorithms/` · Задача темы: реализация собственного движка регулярных выражений. Для всех вариантов определяется общее подмножество синтаксиса и набор тестов.


| № | Задача | Язык | Ветка |
|---|---|---|---|
| 1 | Движок регулярных выражений на DCG-грамматике со встроенным бэктрекингом (рекурсия) | Prolog | 2_task_1_prolog |
| 2 | Движок регулярных выражений с бэктрекингом на продолжениях call/cc (рекурсия) | Scheme | 2_task_2_scheme |
| 3 | Движок регулярных выражений на самописных парсер-комбинаторах и ленивых списках (рекурсия) | Haskell | 2_task_3_haskell |
| 4 | Два движка регулярных выражений под одной сигнатурой, подставляемые функтором (рекурсия) | ML (SML) | 2_task_4_ml |

**2.1 Prolog**. Шаблон разбирается DCG-грамматикой в дерево, а перебор альтернатив и откат при неудаче выполняются средствами поиска Prolog без собственного стека бэктрекинга. Объём кода сравнивается с реализацией явного поиска на C++. Жадность и ленивость квантификатора задаются порядком клауз, обе версии демонстрируются. Отдельно сравниваются три режима на тесте катастрофического бэктрекинга: без таблиц, с табличными вычислениями (`table`, если поддерживаются выбранной реализацией Prolog) и с ручной мемоизацией через `assertz`.

**2.2 Scheme**. Тот же возврат, но собранный руками: матчер пишется в стиле передачи продолжений с явными success- и fail-замыканиями, вторая версия захватывает точки возврата через call/cc и складывает их в стек выборов. Гарантированная стандартом Scheme оптимизация хвостовых вызовов проверяется тестами вложенности шаблона с возрастающей глубиной (до 2000 при достаточных ресурсах); строится таблица глубины, потребления памяти и поведения аналогичных реализаций на Python и C++. В отчёте разбирается, какие вызовы матчера хвостовые, а какие ломает конкатенация узлов.

**2.3 Haskell**. Парсер шаблона собирается из комбинаторов, написанных с нуля: объявляются инстансы Functor, Applicative, Alternative и Monad, после чего квантификаторы * и + берутся из many и some бесплатно. Матчер возвращает ленивый список всех успешных разборов, поэтому режимы «первое вхождение» и «все вхождения» — один и тот же код; различия оцениваются по профилю выполнения, включая затраты памяти. Вторая версия на `ByteString` (базовый пакет экосистемы GHC, не готовый движок регулярных выражений) используется для сравнения со `String` на корпусе в 50 МБ.

**2.4 ML (SML)**. Объявляется сигнатура матчера, под неё пишутся две структуры — бэктрекинг и NFA Томпсона, — и обе подставляются в один и тот же функтор движка без единой правки вызывающего кода. На тестах с большим числом альтернатив сравнивается рост времени работы обеих реализаций (в том числе характерная экспоненциальная деградация бэктрекинга) и эталонов `re` и `std::regex`. Вторым экспериментом в тип узлов добавляется новый вариант, и в отчёт выписывается полный список мест, где компилятор потребовал дописать обработку, — против молчания Python на той же правке.

## Тема 3. Ввод/вывод в консоль и файл

Папка: `3_io/` · Задача темы: файловое KV-хранилище (ключ — значение) с журналом операций и уплотнением. Во всех четырёх реализациях используется общий формат журнала.


| № | Задача | Язык | Ветка |
|---|---|---|---|
| 1 | KV-хранилище с журналом на упаковке строк и корутинном обходе | Lua | 3_task_1_lua |
| 2 | KV-хранилище с журналом на ручных буферах и собственной арене | Odin | 3_task_2_odin |
| 3 | KV-хранилище с журналом на файловых каналах и байт-буферах JVM | Kotlin | 3_task_3_kotlin |
| 4 | То же хранилище на той же JVM в динамическом стиле — замер цены динамики | Groovy | 3_task_4_groovy |

**3.1 Lua**. Бинарные записи журнала пакуются и распаковываются средствами string.pack, индекс ключей хранится в обычной таблице, метатаблицы дают синтаксис обращения к базе как к массиву, а потоковый обход журнала при уплотнении реализуется корутиной — без загрузки гигабайтного файла в память. Главное измерение — накладные расходы рантайма: размер интерпретатора, время старта, память индекса на миллион ключей и скорость записи в одной таблице с Python и C++.

**3.2 Odin**. Та же задача на уровне системного языка: явные срезы байт, defer, множественный возврат вместо исключений и три стратегии выделения памяти под индекс — штатный аллокатор, собственная арена и временный аллокатор для буферов разбора. Сравниваются пиковая память и время загрузки индекса против unordered_map в C++ и dict с его сборщиком мусора в Python. Проверочный тест — потоковое уплотнение журнала объёмом 1 ГБ при лимите памяти 128 МБ на данных, объём индекса которых допускает такой лимит.

**3.3 Kotlin**. Записи читаются и пишутся через файловый канал и байт-буфер с явным порядком байт, ресурсы закрываются конструкцией use, результат команды моделируется sealed-классом, потоковый обход при уплотнении — через sequence. Отдельная таблица посвящена цене виртуальной машины: время старта пустой программы, время первого прогона и выход на плато после прогрева, память при разных настройках кучи, а также сравнение двух файловых API и двух типов буферов между собой.

**3.4 Groovy**. Та же программа, та же JVM, та же стандартная библиотека и тот же формат файла — но в динамическом стиле: обращение к базе через перегрузку операторов индексирования, команды через methodMissing, работа с потоками через замыкания. В сопоставимых условиях оцениваются накладные расходы динамической диспетчеризации; измеряются три режима (динамическое исполнение, проверка типов и статическая компиляция) в одной таблице с Kotlin. При интерпретации учитываются также различия в реализации и прогреве JVM.

## Тема 4. Клиент-серверное взаимодействие

Папка: `4_client_server/` · Задача темы: сетевое KV-хранилище с подпиской на изменения. Для всех вариантов определяется общий протокол взаимодействия.

| № | Задача | Язык | Ветка |
|---|---|---|---|
| 1 | KV-сервер с подпиской в трёх моделях конкурентности: потоки, Ractor, процессы | Ruby | 4_task_1_ruby |
| 2 | KV-сервер с подпиской на процессах, реестре подписок и супервизорах | Elixir | 4_task_2_elixir |
| 3 | KV-сервер с подпиской на ручном мультиплексоре без async/await | Perl | 4_task_3_perl |
| 4 | KV-сервер с подпиской на компилируемом async с переключаемым сборщиком мусора | Nim | 4_task_4_nim |

**4.1 Ruby**. Один и тот же протокол реализуется тремя способами: поток на соединение с учётом GVL в стандартной реализации Ruby, шардированное хранилище на Ractor-ах с настоящим параллелизмом и пул процессов с мультиплексированием внутри. Жизненный цикл соединения описывается блоком с гарантированным освобождением подписок, что сравнивается по объёму кода с RAII в C++ и контекстным менеджером в Python. Итог — сравнение производительности и особенностей GVL в Ruby и GIL в CPython на одинаковой сетевой нагрузке.

**4.2 Elixir**. На каждое соединение заводится процесс, подписки хранит реестр, состояние — сервер-процесс, обработчики живут под супервизором. Сценарий с 10 000 соединений служит витриной рантайма: замеряется память на одно соединение против потоков ОС в C++ и корутин в Python. В режиме отказов часть обработчиков принудительно завершается при идущей нагрузке; строится график изменения пропускной способности и измеряется время восстановления. Вторая версия хранилища на таблице с параллельным чтением сравнивается с сериализующим всё сервером-процессом.

**4.3 Perl**. Сервер пишется как однопоточный цикл опроса дескрипторов с ручными буферами на каждое соединение и ручной досборкой строк — с явным управлением неблокирующим вводом-выводом. Сравнение с эталоном на asyncio и с Nim-версией разбивается по строкам кода отдельно на досборку сообщений и на управление состоянием соединения: так видно, сколько именно кода прячут async и await и сколько это стоит по скорости. Отдельно строится график изменения производительности опроса дескрипторов при росте числа соединений и изучаются ограничения выбранного механизма в сравнении с `epoll`.

**4.4 Nim**. Тот же сервер реализуется на `async`/`await` с циклом событий и асинхронными операциями ввода-вывода. При сравнении с Python `asyncio` учитываются различия рантаймов и реализации, а не только компиляции и интерпретации. Вторым экспериментом для выбранной версии Nim сравниваются доступные режимы управления памятью; при высокой нагрузке измеряются память и высокие перцентили задержки.

## Тема 5. Конвертация данных

Папка: `5_convert/` · Задача темы: конвертация JSON ⇄ NBF, где NBF — собственный бинарный формат с единой спецификацией для всех четырёх программ.


| № | Задача | Язык | Ветка |
|---|---|---|---|
| 1 | Конвертер JSON ⇄ NBF через собственный кодировщик для Codable | Swift | 5_task_1_swift |
| 2 | Конвертер JSON ⇄ NBF как композиция функций над персистентными данными | Clojure | 5_task_2_clojure |
| 3 | Конвертер JSON ⇄ NBF на вариантных типах с исчерпывающим сопоставлением | OCaml | 5_task_3_ocaml |
| 4 | Конвертер JSON ⇄ NBF с кодированием произвольных объектов через рантайм-интроспекцию | Objective-C | 5_task_4_objc |

**5.1 Swift**. Пишется не парсер, а собственный кодировщик и декодировщик для бинарного формата — реализуются протоколы кодирования из стандартной библиотеки, после чего любой тип, помеченный Codable, сериализуется в NBF без единой строки кода на тип. Демонстрация: доменная структура объявляется один раз и сразу пишется и в JSON штатным `JSONEncoder` из Foundation, и в NBF вашим, а добавление нового поля не требует правок ни в одном из них. В таблице это сопоставляется с обходом словаря атрибутов в Python и с необходимостью кодогенерации в C++, с указанием, где именно ошибка обнаруживается — при компиляции или в рантайме.

**5.2 Clojure**. JSON разбирается собственным парсером в обычные персистентные отображения и векторы, поэтому конвертер записывается как композиция чистых функций, а выбор кодирования — мультиметодами по типу значения. При добавлении третьего формата вывода измеряется объём изменений по сравнению с аналогичной правкой в C++. Отдельно измеряется цена персистентности: память и время разбора стомегабайтного файла в персистентных структурах, в их изменяемых аналогах, в словаре Python и в хеш-таблице C++. Четвёртым экспериментом один и тот же кодировщик пишется на мультиметодах и на протоколах — сравнение двух механизмов полиморфизма внутри одного языка.

**5.3 OCaml**. Значение описывается вариантным типом, разбор — взаимно-рекурсивными функциями, предупреждения о неполном сопоставлении настраиваются как ошибки компиляции. Главный эксперимент показывается вживую: в тип добавляется новый вариант, и исследуются сообщения компилятора о местах, где надо дописать обработку; та же модификация проводится в эталонах на Python и C++, чтобы сравнить диагностику и поведение при выполнении. Вторым экспериментом три кодировщика — бинарный, JSON и S-выражения — подставляются в один функтор под общей сигнатурой.

**5.4 Objective-C**. Реализуются две ветки разбора — через штатный сериализатор Foundation и собственным рекурсивным спуском, — а кодировщик NBF обходит произвольный объект через рантайм-интроспекцию, перечисляя свойства класса и разбирая строку их атрибутов, так что кода на каждый класс не требуется вовсе. Это третья точка в главном вопросе темы: Swift описывает соответствие типа и формата протоколом на этапе компиляции, Objective-C — рефлексией в рантайме, Clojure обходится вообще без типов, OCaml кодирует его в типе. Цена рефлексии измеряется напрямую: кодирование миллиона объектов через интроспекцию против прямого кода.

## Сводные результаты

Для каждой из 20 программ фиксируются время выполнения, пиковая память и объём исходного кода. Результаты сопоставляются с эталонами на Python и C++ при одинаковых входных данных **в пределах каждой предметной задачи**. Нормированные показатели скорости и объёма кода сводятся в таблицы и диаграммы; для измерений указываются условия и используемые версии инструментов.

Для перекрёстной проверки совместимости предусмотрены тесты: журнал, записанный на Lua, читается программой на Kotlin; бинарный файл, записанный на Swift, корректно читается на OCaml; общее подмножество регулярных выражений обрабатывается одинаково в Prolog и Haskell; клиент на Perl работает с серверами на Ruby, Elixir и Nim. Совпадение независимых реализаций дополняет отдельные тесты корректности каждой программы.
